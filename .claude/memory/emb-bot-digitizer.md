**Core conventions in the Python pipeline** (get these wrong and output is silently bad, not obviously broken): RGB uint8 internally (cv2 loads BGR — convert on load); color math in CIELAB via `skimage.rgb2lab` on `[0,1]` floats, never cv2's 8-bit Lab; thread-chart snapping uses CIEDE2000, not CIE76 (CIE76 once sent a dark navy to a grey thread in testing); plain Euclidean Lab is fine only for cluster-merge/AA-blend collinearity. Plan-stage coordinates are mm floats, origin at the artwork bbox center, **y-axis down**; the JS engine is **y-axis up**; `digitizer_core/adapter.py` owns the single y-flip between them and should be the only place one ever happens. The service's `/digitize` route deliberately returns an EMB-Bot `Design` object, not a DST — routing that disputed format off the service boundary means a digitized design can't arrive pre-rotated while the DST axis question (below) stays open. To run the Python suite: `cd digitizer && .venv/Scripts/python -m pytest -q` — a bare `python probe.py` will NOT put cwd on `sys.path`; use `python -m pytest` or set `PYTHONPATH=.`.

**Scale, as of the last research pass (exact current counts live in `PRODUCT.md`/`MASTER_SCOPE.md`, they drift):** ~68 thread-brand charts (~19,800 colors) and a 55-font library, all non-ShareAlike after a licensing pass pulled every CC-BY-SA font rather than wait on a legal opinion.

## Decisions

- Started as Kent's own tool because Ink/Stitch felt confusing and he didn't want a subscription. **2026-07-29: pivoted to an explicit market-parity launch benchmarked against Ember** (emberdesign.net) specifically — Wilcom and Hatch are explicitly not the bar.
- Auto-digitizing (photo/logo → stitch file) went from "tabled" to most of the project's engineering effort **in the same week** — Kent supplied a professional build blueprint (Python `digitizer_core` + FastAPI service + review UI in Studio). The original JS engine's image-digitizing path is now frozen/retired in favor of "feed it clean flat art" (Studio's Flatten workflow makes that collapse-to-N-colors step visible to the user); text fonts and DST import stay browser-side permanently.
- Kent gave the digitizer build a standing directive on 2026-07-30: **full autonomy, no questions.** Still the default posture unless he says otherwise.
- Target machine format is Tajima/DST. **No physical sew-out has ever been done on this project.** That's the single biggest ceiling on confidence across the board — fabric-preset accuracy, real stitch quality beyond geometry checks, and the DST axis question all wait on it. Scheduling one is explicitly Kent's call, not something to push for.
- Building a from-scratch auto-digitizer was judged clear on IP grounds before it was built: the foundational patent chain (Goldman/SoftSight, filed 1998) expired around 2018, Wilcom's own granted patents don't cover the approach used here, and Wilcom's own "turning complex fill" application was never granted anywhere. The one place this project is structurally behind commercial tools: they compute contour + skeleton + distance-transform in one raster pass and decide satin-vs-fill from DT statistics; this pipeline rasterizes → vectorizes → re-rasterizes → skeletonizes, so the DT only exists after the decision it should inform. A direct fix (swap the satin/fill classifier to a DT-first rule) was tried and **measured negative** — don't rebuild it from that same recommendation; see `MASTER_SCOPE.md`'s "Measured negatives" for the current writeup.
- Stitch-physics constants (fill spacing, satin density, lock length, etc.) come from measuring a real corpus of pro-digitized DST files (`scratch_corpus/`, Kent's own commissioned files in `scratch_kent/` — both gitignored but not disposable), not from vendor documentation alone, because vendor guidance has been caught wrong at least once: the corpus corrected Wilcom's own published advice on complementary fill-spacing profiles (their recommended profile bulges coverage +33% at both ends; the corpus shows the correct complement is hyperbolic). When a new physics question comes up, measuring the corpus outranks trusting a vendor blog.
- Product policy, one line each: no user-upload design gallery (copyright/moderation exposure) — the curated starter pack is DST-import-sourced instead; no freehand-canvas-as-upload-tile; the thread-chart library deliberately excludes brands from companies that sell embroidery machines/software (Brother, Janome, Viking, Floriani/RNK, Hemingworth were pulled on purpose, not missed); desktop-only at launch; SAM2 ships post-v1 as an opt-in download, not a launch gate — engine quality generally is "a parallel investment, not a launch gate" (Kent's ruling).
- Competitor research lives in its own memory entries, not duplicated here: [[ember-architecture]] (technical teardown — two Next.js apps + iframe, client-side codec usable as a DST reference), [[ember-feature-teardown]] (manual/pricing teardown), [[inkstitch-research]] (Ink/Stitch gap sweep — also where `pystitch`, Ink/Stitch's MIT-licensed pyembroidery fork, was found and has since been adopted as the digitizer's actual format-library dependency).

## Open / unresolved

Cross-checked against `MASTER_SCOPE.md` and `digitizer_core/config.py` directly on 2026-08-14, so this doesn't repeat anything already resolved (e.g. font-license compliance was a hard launch gate as of late July — it's since been resolved by pulling every ShareAlike font, and is no longer launch-gating; not listed below for that reason).

- **DST codec axis bug** — [[dst-codec-axis-discrepancy]]. Five independent sources (including Ink/Stitch's own `pystitch`) agree EMB-Bot's browser DST codec has X/Y transposed vs. the Tajima standard. The fix is understood and written up but not authorized — it would affect every DST EMB-Bot has ever produced, and Kent wants a sew-out or third-party read first.
- **Fill row-spacing (law 19)** — [[fill-density-convention]]. The *measurement* question is settled (pro "density" is quoted between same-direction rows, so EMB-Bot's tatami currently sews at half the professional coverage; satin is unaffected and already correct). The *decision* isn't: halving `FILL_ROW_MM` vs. interleaving two passes at the current spacing both fix the coverage number but sew differently on fabric. Block 2 of the existing sew-out card is the experiment that would decide between them.
- **Chaining (needle-down linking vs. trimming) defaults off** — `chain_links: bool = False`, confirmed current in `config.py`. The corpus-driven trims/1k win this feature was built for (8.42 → 2.63 on the benchmark) is real but isn't what ships: the coverage check that validated it was built from the same artwork polygons the router already trusted, so it structurally could not catch the router being wrong about them — on real fixtures that let up to 29mm of bare cloth get linked instead of trimmed. Re-enabling needs a coverage check built from actually-emitted thread, not polygons, plus a measured `LINK_COVER_TOL_MM` (today a spec value, not a measurement) — both wait on the sew-out.
- **No width floor under satin.** 19 of 162 corpus regions (all photo-class) sew sub-millimetre satin through the stage-7 ladder. A near-free `2·p90 < ~1.0mm → run` reroute is proposed, not built; needs a threshold sweep plus the sew-out.
- **Contour fill stays off by default** — `fill_technique: str = "tatami"`, confirmed current. It shipped behind the flag anyway after a 2026-08-02 adversarial review found three real coverage-measurement gaps (bare core inside ordinary shapes never charged to the starved-area check; that check gates on total area when a widest-bare-spot check is what's actually needed; ring-to-ring transition chords aren't containment-tested). None of the three has been revisited since.
- **Starter design pack and billing/backend** are both blocked purely on a Kent decision (sourcing 12–24 licensed designs; a Stripe-vs-alternatives session), not on engineering — see `PRODUCT.md`.
- **Real-photo stage-0 classification.** A real photograph was once measured landing below the confidence threshold that gates SAM2, `photo_prep`, and the face priors — misclassified as `gradient` at confidence 1.0 — because the corpus at the time held no real-photo fixtures to catch it. Kent parked further investigation into this specific finding; don't reopen unprompted. It's part of why auto-digitize confidence stays low beyond flat spot-color art.

## Gotchas & lessons not already in COOKBOOK.md

COOKBOOK.md's own "Hard-won lessons" section now covers the metric-validation, measure-on-real-art, PowerShell/UTF-8, and pytest-piping lessons this file used to carry — cut here so the two copies don't drift apart. What's left is either Claude-Code-operational (would never end up in a codebase cookbook) or predates COOKBOOK's section entirely:

- **Agents/subagents that die mid-task leave their worktree holding whatever they'd uncommitted.** Before resuming or re-launching, check `git status`/`git diff` in the worktree they were using, and harvest `journal.jsonl` — it holds every completed agent's full return even when the parent workflow itself returns null. Finishing the last mile by hand, inline, beat re-running the whole workflow every time this came up.
- **A module can be committed, imported, and fully documented, and still never execute.** `stage6_border.py` shipped complete and stayed imported for a full session before anyone noticed the sequencing stage never actually called it — every mode was byte-identical whether the module existed or not. An import is not proof of reachability; grep the actual call site.
- **Scoring by the mean hides bimodal defects.** A shape that's ~60% near-white thread and ~40% genuine 24-dE00 color drift scores ~5 dE00 by mean Lab — "defect absent" — because the average lands on a color almost no pixel carries. Score by the median of *per-pixel* error (or a high percentile), not the mean, whenever a region can plausibly hold two populations. The same trap was independently rediscovered in `preflight`'s own artwork-to-thread scoring.
- **When a fix and a measurement instrument disagree, work out which one is wrong before writing either down.** A pooled-median metric once "refuted" a genuine fix for a full day — the refutation got written into both the docs and this memory file before a later per-region rescoring reversed the verdict.
- **Smoke-test by hand before writing formal tests.** Held up across the digitizer's first several build stages: hand-smoke-testing before formalizing pytest coverage found 4-5 real defects per stage that mechanical/determinism-only tests would not have caught (green tests pin properties like "no phantom loops," not "does this look like embroidery").
- **To pull an image the user pasted into chat onto disk without asking them to re-upload it:** walk `~/.claude/projects/<project>/<session-id>.jsonl` for `{"type":"image","source":{"type":"base64"}}` blocks and decode — pasted images aren't written to any temp directory.
- **Windows: never delete a directory junction/reparse point with `rm -rf`** — it follows the link and deletes the real target's contents. Delete the junction itself (e.g. `[IO.Directory]::Delete(path, false)`). Separately: a Windows venv keeps working after the whole folder is moved (`Scripts\python.exe` still runs even though `pyvenv.cfg`'s `home` points elsewhere), but every console-script `.exe` shim breaks silently with no output — regenerate them via pip's own vendored `pip._vendor.distlib.scripts.ScriptMaker` rather than reinstalling from scratch.
- **Svelte (legacy-mode) template calls that close over a prop don't reactively re-run when the prop's contents change** — pass the dependency as an explicit argument instead of closing over it, or part of the UI goes stale silently after a patch.
- **A single `expect()` per array entry over a large fixture (thousands of items) can blow vitest's default 5s timeout.** Collect violations and assert on the aggregate instead of per-entry.
- **The in-app preview pane's storage is ephemeral across pane restarts** — a pane restart can look exactly like a real persistence bug. Verify persistence logic through the actual serialize/deserialize functions (via module import), not by reloading the preview pane.
