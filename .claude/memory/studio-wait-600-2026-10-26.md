2026-10-26, Kent: "Wait up to 600 s (Recommended)". Follows
[[digitize-speed-2026-10-26]], which found the mismatch: the Studio gave up at
300 s and told the customer the job "was stopped" while the service kept
computing it for up to 600 s (`jobs.py` JOB_TIMEOUT_S, counted from RUNNING).

**Built:**
- `pollJob` waits SERVICE_JOB_TIMEOUT_MS (600 s) + POLL_GRACE_MS (30 s).
- A running job is timed from the first poll that READ "running". The poll
  carries no start time, and that read is at or after the service's own
  start, so the service's verdict, in its own words, always arrives first.
- A job still queued is timed from the first poll, so a stuck worker still
  ends the wait.
- `onState(state, {runningMs})`. Past LONG_RUN_MS (the old 300 s), the
  existing `.dgp-status` line reads "Still digitizing…".
- TIMEOUT_DIGITIZE now says the Studio stopped WAITING after ten minutes,
  never that the job was stopped.
- `photo_prep_background_removal_timeout_s` is 120 (was 60). The MFab hat's
  cutout ran 49-53 s on a loaded laptop, and past the limit the photo
  digitizes with its background left in.

**Not changed:** the service's own TIMED_OUT text ("…was stopped") is still
half true: the thread runs on and its result is discarded.

**Trap:** Playwright's `reuseExistingServer` (local, not CI) will serve
ANOTHER worktree's code if that tree's Vite is still on the port (5183). A
stopped e2e run left one, and the new spec failed against the old code.
Check `Get-NetTCPConnection -LocalPort 5183` before an e2e run in a fresh
lane.
