# `tie_in_off` — 2026-10-22

**The brief's premise was wrong.** It asked for `tie_only_at_cuts`: "the pro
locks only where the thread is cut, we lock every run". Measured, neither half
holds.

- **Ours already ties only at cuts.** `stitches.apply_ties` ties a run's start
  only if it is the block's first run or `run.trim`. A run reached by a plain
  jump or continuation gets none. A `tie_only_at_cuts` flag would have been a
  byte no-op.
- **The pro locks none, cut or not.** Every pro run start in the three hat
  DSTs follows a trim or colour change (no uncut jumps), and 1 of 68 is locked.

*Bean-retrace false positives: a three-pass bean opens `p0 p1 p0 p1` by
itself. The plan census (Fremont) has no tied-in run without a trim except
3 bean/retrace runs. Never detect a lock by shape; `StitchRun.tie_in_pts`
records what `apply_ties` prepended.

**Built (OFF).** `cfg.tie_in_off`: `stitches.drop_tie_ins(blocks)` at the end
of `sequence()` strips exactly `tie_in_pts` leading points of each run;
tie-offs stay. DST stitches saved ON vs OFF: Fremont 232, Becker 192,
MFab 252. Not built: the JS `ties` builder (OFF everywhere, flag-gated, so no

start holds without a knot is a sew-out (ROADMAP gate 1): Kent flips after it.
