# Photo/Gradient Digitizing — Steps 1–2: Classifier + Gradient Blend Tier

Status: DRAFT for adversarial critique. Implements steps 1–2 (of 10) from
`docs/photo-digitizing-plan-2026-07-31.md`, the plan that supersedes the old
blanket "flat art in, pro out" ceiling with a per-class ceiling. Steps 3–10
(background removal, face detection, the SLIC/RAG photo region-former,
direction fields, streamline/portrait tier, sew-out gate) are explicitly
**out of scope** here — see Non-goals.

## Why these two steps first

Cheapest, fastest, most self-contained slice of the source plan: no new
heavy deps (no rembg, no opencv-contrib swap, no SLIC/RAG), no patent-adjacent
territory (that's step 8 only), and step 2 directly answers the complaint
that started the Python digitizer effort — Kent's drone-render hat coming out
as flat-quantized mush. Everything here is additive to the existing stage1–7
pipeline; the flat-art lane is a hard, tested invariant.

## Scope

- `stage0_classify.py` — 4-way input classifier (flat / gradient /
  photo-subject / photo-scene), user-overridable, runs before stage 1.
- Per-class ceiling copy surfaced through the preflight warnings channel
  (existing mechanism — new warning codes, not a new UI surface) — replaces
  the blanket "feed it flat art" messaging judgment with an honest,
  per-class one.
- `stage6_blend.py` — new fill tier (sibling to `stage6_fill.py` /
  `stage6_satin.py` / `stage6_border.py`): ramp detection → 3–5 chart-shade
  decomposition → interleaved tatami layers. Only invoked when the global
  classification is `gradient`.
- **Hard invariant, tested explicitly:** classification `flat` (including
  every existing fixture and every real design in the corpus) produces a
  **byte-identical plan** to today. This is the same discipline as every
  prior "additive, back-compat" change in this codebase — nothing about
  today's flat-art lane may change as a side effect of adding these two
  files.

## `stage0_classify.py` contract

`classify(raw_image: bytes|path, cfg) -> Classification{class_: Literal["flat","gradient","photo_subject","photo_scene"], confidence: float, signals: dict, warnings: [...]}`

- **Signals** (all cheap, no new deps — cv2/skimage already have everything):
  - `unique_color_mass`: fraction of pixels whose color, after a light
    quantize (existing stage-2-style k-means at k=16, throwaway), differs
    from their local 3×3 mode. Flat art → near zero; photos → high.
  - `gradient_smoothness`: mean local variance of the Sobel gradient
    magnitude over non-edge regions. Low variance + non-zero gradient
    magnitude = smooth ramp (gradient class); near-zero magnitude
    everywhere = flat; high variance = photographic texture.
  - `alpha_softness`: if an alpha channel exists, fraction of alpha values
    strictly between 8 and 247 (soft edge) vs. binary-ish. Photo cutouts
    trend soft; flat logo exports trend binary.
- **Decision**: simple thresholded decision tree over the three signals, not
  ML — thresholds tuned against the fixture set below and recorded as named
  constants in `machine.py`-style (not magic numbers inline). Ties/low
  confidence fall to `flat` (the safe, already-proven default) with a
  `CLASSIFICATION_UNCERTAIN` warning rather than silently guessing photo.
- **`cfg.forced_class`**: when set, skip signal computation entirely and use
  it — the escape hatch for both testing and the eventual UI override
  mentioned in the source plan.
- **New warning codes** (`warnings_codes.py`, "Stage 0" section):
  `CLASSIFIED_GRADIENT`, `CLASSIFIED_PHOTO_SUBJECT` (carries the
  per-class ceiling copy string — "portrait/pet handling isn't built yet,
  results will be low quality" until step 3+ ships),
  `CLASSIFIED_PHOTO_SCENE` (same, scenery-specific copy),
  `CLASSIFICATION_UNCERTAIN`.
- **The byte-identical invariant lives here structurally**: `pipeline.py`
  only branches on `classification.class_ == "gradient"` to invoke
  `stage6_blend`; every other class (`flat`, and — until steps 3–8 exist —
  `photo_subject`/`photo_scene` too, which fall through to today's pipeline
  with just the honest warning attached) takes the exact same code path as
  before this change existed.

## `stage6_blend.py` contract

`blend_fill(region: Region, source_pixels, cfg) -> [StitchRun]` — same
return shape as `stage6_fill.py`'s tatami emitter, so stage 7 sequencing
treats it identically to any other fill tier.

- **Ramp detection**: within the region's original (pre-quantize) pixel
  data, fit a low-order structured residual (linear or radial gradient
  model) vs. the flat quantized color. Structured residual (low local
  variance, systematic direction) → real ramp, proceed. High local variance
  (speckle/noise) → not a ramp, fall back to ordinary tatami — this is the
  same "validate the metric on known-clean fixtures first" discipline
  already established in this codebase (the satin-fan-angle metric hygiene
  rule).
- **Shade decomposition**: 3–5 shades, chosen via Ostromoukhov–Hersch
  barycentric coverage against the existing thread chart (reuses the
  existing ΔE00 nearest-thread code from `threads.py` — this is selection
  math, not a new color model implementation beyond the barycentric split).
- **Emission**: N interleaved tatami layers, **one common fill angle**
  (reuses `stage6_fill.py`'s angle logic — do not re-derive), per-layer row
  spacing = `0.4mm × N`, rows phase-offset between layers so total emitted
  coverage sums to 1.0–1.2. This is parameterizing the existing tatami
  emitter, not new stitch geometry — flagged as such in the source plan and
  worth re-confirming in review, since it's the whole reason this step is
  cheap.
- **Only ever called when `classification.class_ == "gradient"`** — never
  invoked on a flat-classified design, which is what makes the
  byte-identical invariant checkable by a single `if` at the call site.

## Preflight / warning-copy changes

No new UI surface — reuse the existing preflight warnings channel. Add the

"honest copy" half of step 1 from the source plan, and it's the concrete

## Tests

1. **Flat-lane byte-identical** (`test_flat_lane_byte_identical.py`): run
   every existing committed test fixture (`logo_whitebg.png`, `logo_alpha.png`,
   the pro-corpus benchmark files if licensing allows offline use) through
   the pipeline with these changes present vs. a stashed pre-change baseline;
   assert identical shape_ids, warnings, and stitch coordinates. This is the
   one test that must never go red — if it does, the change is wrong, not
   the test.
2. **Classifier routing**: `enthusiast_logo.png` → `flat`; `drone_render.png`
   → `gradient`; `photo_subject_stub.png` → `photo_subject`;
   `photo_scene_stub.png` → `photo_scene`; a synthetic ambiguous fixture
   (flat art with one soft drop-shadow) → either a stable class or
   `CLASSIFICATION_UNCERTAIN`, never a crash.
3. **Gradient blend geometry** (`gradient_ramp_linear.png`/`_radial.png`,
   from `make_gradient_fixture.py`, seeded/deterministic): measured from
   **emitted stitch rows, not planned config** — per-layer spacing =
   `0.4 × N mm ± 0.02mm`; Σ coverage in `[1.0, 1.2]`; shade count in `[3,5]`;
   exactly one fill angle shared across all layers of one blend group.
4. **Drone-render A/B** (`drone_render.png` at 90mm): render today's flatten
   output vs. this pipeline's gradient output side by side (debug PNG, human
   review — this is the acceptance gate the source plan calls "render A/B
   vs today's flatten shows no banding at arm's length," not a pixel-diff
   assertion).
5. **Classification determinism**: same input classified twice → identical
   class + confidence (no RNG in the signal computation, so this should be
   free, but pin it as a canary anyway per this codebase's established
   pattern).

## Debug artifacts (`cfg.debug_dir`)

`stage0_classification.txt` (class, confidence, raw signal values — the
review record for why a design routed where it did), `stage6_blend_shades.png`
(swatch strip of the N decomposed shades per blend group),
`stage6_blend_rows.png` (row-by-row render of the interleaved layers before
merge — makes phase-offset bugs visible immediately).

## Environment

No new dependencies. `cv2`/`skimage` already provide everything both stages
need (Sobel, k-means, ΔE00) — confirmed present in the existing
`digitizer/.venv`. The `opencv-contrib-python` swap, `rembg`, and
`cv2.FaceDetectorYN` are step 3 concerns, not touched here.

region-former (step 4), direction fields / ETF (step 5), mono tonal tiers
