# VTracer — Research Evaluation

Evaluated whether [visioncortex/vtracer](https://github.com/visioncortex/vtracer) (a Rust raster-to-vector tracer) would benefit either of EMB-Bot's two tracing surfaces: the Python auto-digitizer pipeline (`digitizer/digitizer_core/`) and the Svelte manual digitizing tool (`app/`). Grounded in vtracer's own primary sources (GitHub repo, source, design docs, Cargo.toml, crates.io, docs.rs, PyPI, npm) plus hands-on testing: `pip install`ed the actual published package on this Windows 11 / Python 3.14.6 machine and ran real conversions on synthetic test images, the same way `docs/shape-tracer-evaluation.md` ran shape-tracer live rather than trusting its README alone. Repo and EMB-Bot codebase left unmodified; all test artifacts live outside the repo.

## What was checked

- vtracer's GitHub repo: [README](https://github.com/visioncortex/vtracer/blob/master/README.md), [LICENSE](https://github.com/visioncortex/vtracer/blob/master/LICENSE), [`Cargo.toml`](https://github.com/visioncortex/vtracer/blob/master/Cargo.toml) (workspace) and per-crate manifests, [`CHANGELOG.md`](https://github.com/visioncortex/vtracer/blob/master/CHANGELOG.md), the design docs under `docs/design/` ([architecture.md](https://github.com/visioncortex/vtracer/blob/master/docs/design/architecture.md), [mosaic.md](https://github.com/visioncortex/vtracer/blob/master/docs/design/mosaic.md), [roadmap.md](https://github.com/visioncortex/vtracer/blob/master/docs/design/roadmap.md)), and a golden SVG test fixture ([`ring_spline.svg`](https://github.com/visioncortex/vtracer/blob/master/crates/vtracer/tests/goldens/ring_spline.svg)), read for real path data rather than taken on faith.
- Package registries: [crates.io](https://crates.io/crates/vtracer) (crate + [version history](https://crates.io/crates/vtracer/versions) via its JSON API), [docs.rs](https://docs.rs/vtracer), [PyPI](https://pypi.org/project/vtracer/) (including its [JSON API](https://pypi.org/pypi/vtracer/json)), [npm](https://www.npmjs.com/package/@visioncortex/vtracer) / [npm registry API](https://registry.npmjs.org/@visioncortex/vtracer), and the project's own site, [visioncortex.org/vtracer](http://www.visioncortex.org/vtracer/).
- Hands-on: created an isolated venv, ran `pip install vtracer`, generated three synthetic PNGs (a ring/donut, two touching same-colour circles, two touching different-colour circles — mirroring the exact scenario shape-tracer-evaluation.md flagged as a gap), and ran real conversions through the installed package, inspecting the raw SVG output byte-for-byte.
- EMB-Bot's own code: `digitizer/digitizer_core/stage2_quantize.py`, `stage2_photo_segment.py`, `stage3_segment.py`, `stage4_vectorize.py`, `config.py`, `digitizer/requirements.txt`, `digitizer/pyproject.toml`, `app/package.json`, `app/src/lib/imageRegions.js`, and `docs/shape-tracer-evaluation.md` in full.

## Findings

### Project shape: three loosely-coupled ecosystems, not one version

vtracer ships as three independently-versioned artifacts, and they are currently **not in sync**:

| Ecosystem | Latest published | Date | Notes |
|---|---|---|---|
| Rust crate (`vtracer`, [crates.io](https://crates.io/crates/vtracer)) | stable `0.6.5`; prerelease `1.0.0-alpha.3` | `0.6.5`: 2025-10-17; `1.0.0-alpha.3`: 2026-08-01 | Crate created 2020-10-31, 74,932 lifetime downloads (crates.io API) |
| Python (`vtracer`, [PyPI](https://pypi.org/pypi/vtracer/json)) | `0.6.15` | wheel uploaded 2024-03-29 | No `1.0.0-alpha.*` published — see below |
| npm (`@visioncortex/vtracer`, [registry](https://registry.npmjs.org/@visioncortex/vtracer)) | `1.0.0-alpha.3` | 2026-08-01 | No `0.x` release ever existed on npm |

The GitHub `master` branch is mid-way through a documented rewrite: [`CHANGELOG.md`](https://github.com/visioncortex/vtracer/blob/master/CHANGELOG.md) describes `1.0.0-alpha.1` (2026-07-24) as a "complete rewrite establishing VTracer as a vectorization framework with pluggable stages," adding a Node/WASM package and a pyo3-based rewrite of the Python bindings; `1.0.0-alpha.2` (2026-07-27) adds watershed clustering and a breaking rename (`color_mode` → `clustering`); `1.0.0-alpha.3` (2026-08-01) adds a fidelity-benchmark crate. [`docs/design/roadmap.md`](https://github.com/visioncortex/vtracer/blob/master/docs/design/roadmap.md)'s milestone 5 ("Bindings") explicitly plans "the npm package under `nodejs/`; delete `webapp/`; CI covers crates.io + PyPI + npm releases" — npm is done, **PyPI is not**: a direct query of PyPI's release JSON found no version containing `1.0`, `alpha`, or `a1`/`a2`/`a3`, even though the *current* [`crates/vtracer-py/README.md`](https://github.com/visioncortex/vtracer/blob/master/crates/vtracer-py/README.md) instructs `pip install vtracer==1.0.0a3` — that command would fail today. Separately, `webapp/` (the CHANGELOG says "removed" and `Cargo.toml` excludes it from the workspace build) is nonetheless still fully present in the current tree with all its source files — best read as orphaned rather than either "removed" or "supported."

Practical read: **what EMB-Bot can actually `pip install` today is the old, pre-rewrite `0.6.15` API** (confirmed directly — see below) — not the watershed clustering, fixed-palette snapping, or "true mosaic" hole handling the current README/website describe, all of which are `1.0.0-alpha`-only and live only in the Rust crate and the npm/WASM build.

### Algorithm (current `master` / 1.0-alpha framework)

Per [`docs/design/architecture.md`](https://github.com/visioncortex/vtracer/blob/master/docs/design/architecture.md), the pipeline is a chain of pluggable stages: **Frontend** (segmentation — `ColorClusterFrontend`, `BinaryFrontend`, or `WatershedFrontend`) → **ColorFitter** (`Identity`, `FixedPalette` — OKLab nearest-colour snap, confirmed again in [`roadmap.md`](https://github.com/visioncortex/vtracer/blob/master/docs/design/roadmap.md) milestone 3 — or `AutoQuantize`) → **Compositing** (stacked or mosaic) → **CurveFitter** (`PixelFitter`, `PolygonFitter`, or `SplineFitter` with corner detection) → **CurvePasses** (simplify) → **OptimizerPasses** (coordinate quantization, shortest-encoding SVG writer). Spline-mode curve fitting uses Philip Schneider's classic cubic-Bezier-fitting algorithm via the `flo_curves` crate dependency (named directly in `Cargo.toml`'s own dependency comment) — confirmed empirically too: every SVG this project generated, both the shipped [`ring_spline.svg`](https://github.com/visioncortex/vtracer/blob/master/crates/vtracer/tests/goldens/ring_spline.svg) golden and my own hands-on output, contains genuine `C`/`c` cubic-Bezier path commands, not polylines dressed up as curves.

**Hole representation — verified empirically, and it depends on the hierarchical mode:**

`docs/design/mosaic.md` states holes are encoded via `fill-rule="nonzero"` with an outer contour and its hole wound in opposite directions inside *one* `<path>`'s `d` string ("the island uses the result forward as its outline, the enclosing region uses it reversed as a hole — same cached object"). I confirmed this two ways:

1. Reading `ring_spline.svg` directly: one `<path>` contains two subpaths (an outer square, an inner blob) with no `fill-rule` attribute at all (SVG defaults to `nonzero`).
2. Running my own ring/donut test image through the actual installed `0.6.15` package. Result differs sharply by `hierarchical` setting:
   - **`hierarchical="stacked"` (the default)**: the navy ring is *not* emitted as one path with a hole. It comes out as three opaque, z-ordered paths — a full-canvas navy square, painted over by a white shape with a hole-shaped subpath, painted over again by a smaller solid white circle — and the ring only exists as an emergent effect of paint order. Recovering "the navy region as a single polygon with a hole" would require boolean geometry across the whole layer stack, not a per-path parse.
   - **`hierarchical="cutout"`**: the SAME ring comes out as one `<path>` per colour, and the navy path itself has two subpaths (outer ring boundary + inner hole boundary) — a clean, direct match for `shapely.geometry.Polygon(shell, holes=[...])`.

   `roadmap.md` milestone 4 notes `--hierarchical cutout` was "switched to the true mosaic" only as part of the 1.0 rewrite, implying the `cutout` mode in the currently-`pip install`able `0.6.15` is an older, pre-mosaic implementation — real and clean for a single region's own hole (just demonstrated), but not verified by me for gapless-tessellation quality across many adjacent regions in a busy multi-colour image.

Three drawing modes exist (`mode`): `pixel` (unit-square mosaic, aimed at pixel art), `polygon` (straight-line simplified polylines), `spline` (the Bezier default).

### Integration paths

**CLI / Rust crate** — not a natural fit. EMB-Bot has no Rust anywhere in its stack; standing up a Rust toolchain (or shelling out to a separately-built CLI binary) just to call a tracer is real infrastructure for both the Python service and the browser app.

**Python bindings (`pip install vtracer`)** — real Windows support, confirmed two ways: PyPI's file listing shows prebuilt wheels across CPython 3.10–3.14, PyPy 3.8–3.11, Windows (x86/x86-64/ARM64), macOS, and manylinux/musllinux Linux; and `pip install vtracer` on this actual machine (Windows 11, Python 3.14.6) pulled `vtracer-0.6.15-cp314-cp314-win_amd64.whl` and installed cleanly with **no Rust toolchain present on the machine** (`where cargo rustc` found nothing). The installed API, read straight from `help(vtracer.convert_image_to_svg_py)` on the actual package (not the docs), is three flat functions — `convert_image_to_svg_py`, `convert_pixels_to_svg`, `convert_raw_image_to_svg` — no `Config` class, confirming this is the pre-1.0 API. Its own SVG generator comment reads `VTracer 0.6.12`, which doesn't match *any* version in crates.io's own history for the core crate — the Python binding vendors its own core version, decoupled from crates.io's published releases.

**A real bug, found empirically:** calling `convert_image_to_svg_py` with *any* keyword argument segfaults immediately (exit 139) on this Python 3.14.6 / Windows setup. This reproduced 100% of the time across all eleven individual keyword arguments tested one at a time (`colormode`, `hierarchical`, `mode`, `filter_speckle`, `color_precision`, `layer_difference`, `corner_threshold`, `length_threshold`, `max_iterations`, `splice_threshold`, `path_precision`) — only the zero-argument, all-defaults call worked. **Workaround confirmed**: calling with the same values as *positional* arguments works fine (used to produce the cutout-mode result above), so this looks like a PyO3 keyword-argument-marshaling bug specific to Python 3.14's C API in a wheel built in 2024 — plausibly already fixed on `master`, which has since moved to pyo3 0.26 (`crates/vtracer-py/Cargo.toml`). **I could not test this on Python 3.12**, EMB-Bot's own pinned floor (`digitizer/pyproject.toml`: `requires-python = ">=3.12"`; only 3.14 is installed on this machine) — this needs to be re-verified on EMB-Bot's actual target interpreter before any integration work, not assumed safe or broken.

**npm / WASM, for the Svelte app** — the package is real WebAssembly (confirmed via `nodejs/package.json`: files are `pkg/vtracer_wasm.js` + `pkg/vtracer_wasm_bg.wasm`, no CPU/OS restriction), but it is **not** built for direct browser use. Its own build script is `wasm-pack build --target nodejs`, which produces a CommonJS module that loads the `.wasm` via Node's synchronous `fs.readFileSync` — the standard wasm-pack Node target, not `--target web` or `--target bundler`, which is what a Vite-bundled, client-only app (`app/`, package `emb-bot-studio`, no Node backend in `app/package.json`) needs. Using it as-is in the Svelte app isn't a supported path; EMB-Bot would need to rebuild the WASM bindings themselves from `nodejs/src/lib.rs` with a different wasm-pack target, adding a Rust + wasm-pack step to a build that currently has none. The repo does contain an actual historical browser demo (`webapp/`, webpack + wasm-bindgen — see its own build steps in [`webapp/Readme.md`](https://github.com/visioncortex/vtracer/blob/master/webapp/Readme.md)), but per the versioning section above it's excluded from the active workspace and orphaned, not a reliable starting point.

### Config knobs — vtracer (0.6.15, what's actually installable) vs. EMB-Bot vs. shape-tracer

Confirmed against both [PyPI's own project description](https://pypi.org/project/vtracer/) and the installed package's real signature:

| vtracer 0.6.15 param | Default | Role |
|---|---|---|
| `colormode` | — | `'color'` / `'binary'` |
| `hierarchical` | — | `'stacked'` / `'cutout'` (see hole finding above) |
| `mode` | — | `'spline'` / `'polygon'` / `'none'` |
| `filter_speckle` | 4 (px) | speckle/despeckle floor |
| `color_precision` | 6 (bits/channel) | quantization depth |
| `layer_difference` | 16 | raw colour-distance merge threshold between layers |
| `corner_threshold` | 60° | corner-vs-curve decision angle |
| `length_threshold` | 4.0 px | minimum segment length |
| `max_iterations` | 10 | Bezier-fit refinement cap |
| `splice_threshold` | 45° | curve segment splice angle |
| `path_precision` | 8 | output decimal places |

1.0-alpha adds `clustering='watershed'`, `simplify` (tolerance px), `palette=[hex,...]` (fixed-palette snap), `max_colors`, `optimize` (0/1/2 SVG-encoding aggressiveness), and adaptive-threshold controls — none of this is in `0.6.15`, confirmed by the installed package exposing no `Config` class at all.

Compared to EMB-Bot's own tunables: `digitizer/digitizer_core/config.py` sets `simplify_tol_mm: float = 0.2` (mm, converted to px via `px_per_mm` before feeding `cv2.approxPolyDP`) and `min_detail_mm: float = 1.5` (the sewable-area floor) — the same basic *shape* of knob (a simplify tolerance + a minimum-feature floor) as vtracer's `length_threshold`/`filter_speckle`, but EMB-Bot's is physically dimensioned (ties to what's actually sewable) where vtracer's is pixel-native with no size awareness. `app/src/lib/imageRegions.js` (the Svelte app's own *existing* flatten-to-regions tracer, separate from the shape-tracer evaluation) uses `SIMPLIFY_TOL = 1.6` px and `DESPECKLE_SHARE = 0.0004` (fraction of image area). shape-tracer, per `docs/shape-tracer-evaluation.md`, exposes exactly one tolerance slider (default 2, Douglas-Peucker) plus a `MIN_AREA` speckle floor. vtracer's knob set is considerably richer than either — more control, also more surface area to mistune for a tool meant to give a good result by default.

### What vtracer claims about itself vs. other tracers

Only qualitative claims found, no published numbers: the [README/site](http://www.visioncortex.org/vtracer/) says it "skips Potrace's expensive optimal-polygon search in favor of a fast, linear pipeline," and that its stacked-mode output is "much more compact" than Adobe Illustrator's Image Trace because it avoids emitting shapes with holes (the exact behaviour independently confirmed above). A dedicated fidelity-benchmark tool now exists (`crates/vtracer-bench`, added in `1.0.0-alpha.3`, self-described as "a blind fidelity benchmark for raster-to-vector tracers" using PSNR/SSIM), but its own [README](https://github.com/visioncortex/vtracer/blob/master/crates/vtracer-bench/README.md) only publishes self-calibration numbers (JPEG quality 95 vs. original scores 0.9502; 0.8px Gaussian blur scores 0.8443) — no head-to-head results against potrace, ImageTracer.js, or anything else were found anywhere in the project's own materials.

### Head-to-head against shape-tracer's two named gaps

`docs/shape-tracer-evaluation.md` flagged two gaps in shape-tracer: (1) same-colour touching shapes merge into one contour, and (2) vertices have no per-point tangent handle, so edits near corners kink instead of bulge. Checked both directly:

1. **Same-colour merging**: reproduced identically in vtracer. Two touching, identically-coloured circles traced as one single path in every mode tested — this is not a shape-tracer weakness, it's inherent to tracing pixel connectivity (two same-coloured touching shapes *are* one connected blob in the raster), and EMB-Bot's own `stage3_segment.py` has the identical limitation (`ClassicalSegmenter` is literally `cv2.connectedComponents` per colour layer). Not a real differentiator.

   What vtracer *does* do better: two **differently**-coloured touching shapes separated cleanly into two correctly-coloured paths with a clean shared boundary, confirmed on my own test image. shape-tracer's single background-distance threshold is blind to hue entirely, so it would merge that case too (per its own README limitation, confirmed hands-on in the evaluation doc). For logo-style art (multiple thread colors, the primary case for a digitizing tool), this is a genuine, narrower win — it solves the common case, not the identical-colour edge case.

2. **No tangent handles**: vtracer's spline mode outputs real cubic Bezier curves (`C`/`c` commands with two control points per segment), confirmed directly in both the shipped golden fixture and my own generated output — structurally the opposite of shape-tracer's plain-point Catmull-Rom representation. Cubic Bezier control points *are* tangent handles. This is a genuine structural advantage **if** the Svelte editor is built to parse and manipulate Bezier anchors/handles directly — that's real, non-trivial editor UI work either way, vtracer only supplies data that makes it possible rather than solving it outright.

## Verdict

**Python pipeline (`digitizer_core`): skip a wholesale port; not worth adopting today.** Color segmentation is solved upstream (stage2's Lab k-means / SEEDS+RAG already assign pixels to a fixed thread chart; vtracer's clustering — even the 1.0-alpha `FixedPalette` OKLab snap — doesn't know about a thread chart and isn't in the installable version anyway). The one theoretically interesting piece — real Bezier curve fitting in place of `cv2.approxPolyDP` polylines — is undercut by everything found above: the installable `0.6.15` is old and stale relative to the actively-developed core; it segfaults on every keyword-argument call on this machine (workaround exists — positional args — but this needs re-verification on EMB-Bot's actual pinned Python 3.12 before it's trusted at all); its default hierarchical mode does not map cleanly to `shapely` polygons-with-holes (`cutout` does, but is itself the old pre-"true-mosaic" implementation); and `stage4_vectorize.py` already carries real, hard-won correctness logic (self-intersection recovery via `_polygon_parts`/`make_valid`, the post-simplify thread-colour revalidation pass fixing a real dE00-23.9 defect) that a Rust black box would bypass rather than replace. If anything is worth a narrow, time-boxed spike, it's borrowing the *idea* — real curve fitting instead of polyline simplification — rather than the dependency; not a port.

**Svelte manual digitizing tool (`app/`): also not ready to adopt, but for a different reason — no working browser path exists.** Note first that this only concerns the separate "auto-trace then drag vertices" feature `docs/shape-tracer-evaluation.md` evaluated — the app's existing auto-flatten pipeline (`app/src/lib/imageRegions.js`) already has its own working hole-aware tracer and isn't in question. On the merits, vtracer looks genuinely competitive with shape-tracer on both of its named gaps (real Bezier tangent data; better multi-colour separation) — but there is currently no drop-in way to run it client-side: the published npm package targets Node, not the browser, and the one artifact that *was* built for the browser (`webapp/`) is orphaned. Using it would mean standing up a Rust + wasm-pack build step from scratch in a Svelte/Vite app that has none today, just to reach parity with shape-tracer, which already works with zero new build tooling and already has a hands-on-positive evaluation on record. Recommendation: proceed with shape-tracer per that evaluation's own verdict; revisit vtracer's WASM path only if EMB-Bot ends up needing a Rust/WASM build step for an unrelated reason, not as a reason to build one now.
